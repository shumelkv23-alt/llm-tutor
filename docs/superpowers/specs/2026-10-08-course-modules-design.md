# Дизайн: десять модулей курса

> Дата: 2026-10-08. Расширяет курс с одной темы (topic01 «Pandas / EDA») до
> всех десяти тем mlcourse.ai. Затрагивает граф (§3 архитектуры), маршрут
> (§6.2–6.4) и анкету (`2026-10-08-adaptive-survey-design.md`). Принцип
> проекта не меняется: LLM объясняет и предлагает, а состояние ученика,
> вердикты и закрытие узлов считает код. Генератор черновиков, который
> обсуждался в брейншторме, отложен (§9).

## 1. Зачем

Сейчас в боте одна тема из десяти. Ученик должен пройти весь курс: каждый
модуль ему объясняет тьютор, вместе они решают задания, как сейчас в topic01.

Тема 1 зашита в код в нескольких местах:

| Где | Что |
|---|---|
| `course/seed.py` | один путь `data/seed_topic01.json` |
| `student/survey.py` | блоки анкеты (`BLOCKS`), вопрос об уровне про pandas |
| `llm/prompts.py` | три системных промпта «тема 1 «Pandas / EDA»» |
| `bot/start.py` | приветствие «тьютор по теме «Pandas / EDA»» |
| `db/repos.replace_seed` | гасит (`active=0`) всё, чего нет в загружаемом файле, поэтому seed тем по очереди грузить нельзя: каждая следующая тема погасит предыдущую |

Контента для тем 2–10 нет: нужно написать около 180 узлов и 400 заданий.

## 2. Решения (согласованы)

1. **Десять модулей**, как в mlcourse.ai. Для ученика часть курса называется
   **«модуль»**, а узел графа остаётся **«темой»**. Поэтому все нынешние
   тексты («✅ Закрыть тему», «закрой тему») сохраняют смысл.
2. **Один граф на весь курс.** Модуль — это атрибут узла. Межмодульные рёбра
   разрешены **только назад**: узел модуля N может требовать узлы модулей ≤ N.
3. **Межмодульные рёбра по умолчанию мягкие** (`hard=false`): это штраф к
   приоритету, а не блокировка. Жёсткое межмодульное ребро допустимо, но
   валидатор предупреждает о нём.
4. **Порядок по умолчанию 1 → 10.** Доказанное знание перестраивает маршрут.
   Вперёд — через анкету модуля и проверку заявленного. Назад — через
   просевшее владение узлом прошлого модуля.
5. **Анкета на входе в каждый модуль.** Логика та же, что сейчас (уровень →
   блоки → ранний выход), конфиг анкеты лежит в seed модуля.
6. **Одна БД.** Seed по-прежнему лежит по файлу на модуль, но в БД все файлы
   загружаются одним проходом.
7. **Контент модулей 2–10 пишет Claude вручную** по материалам mlcourse.ai,
   по образцу topic01. Каждый модуль проходит адверсариальное ревью (§6.3).
   Генератор черновиков отложен (§9).

Модули:

| № | Название |
|---|---|
| 1 | Первичный анализ данных с Pandas |
| 2 | Визуальный анализ данных |
| 3 | Классификация, деревья решений и kNN |
| 4 | Линейные модели классификации и регрессии |
| 5 | Бэггинг и случайный лес |
| 6 | Построение и отбор признаков |
| 7 | Обучение без учителя: PCA и кластеризация |
| 8 | Обучение на гигабайтах: SGD и Vowpal Wabbit |
| 9 | Анализ временных рядов |
| 10 | Градиентный бустинг |

## 3. Данные и граф

### 3.1 Seed-файл модуля

Один файл на модуль: `data/seed_topicNN.json` (NN = 01…10). К нынешним разделам
(`nodes`, `edges`, `items`, `rubrics`, `criteria`) добавляется раздел `topic`:

```json
"topic": {
  "number": 2,
  "title": "Визуальный анализ данных",
  "intro": "Строим графики: matplotlib, seaborn, t-SNE…",
  "survey": {
    "level_key": "t02_level",
    "level_question": "Как у тебя с графиками в Python?",
    "level_options": ["С нуля", "Немного рисовал", "Уверенно строю графики"],
    "blocks": [
      {"key": "t02_plots", "title": "…", "question": "…",
       "example": "…", "concepts": ["…"]}
    ],
    "assumed_by_confident": ["t02_plots"],
    "foundation": ["t02_plots"]
  }
}
```

Узлам поле модуля в JSON не нужно: загрузчик проставляет `topic_id` по файлу.

Анкета topic01 переезжает из `student/survey.py` в `seed_topic01.json` без
изменений. Её ключи (`survey_level`, `block_python`, `block_tables`,
`block_loading`, `block_selection`, `block_analysis`) **не меняются**: на них
уже записаны факты в рабочей БД. Ключи новых модулей начинаются с `tNN_`.

**Диапазоны id.** У topic01 id остаются как есть. Модуль N берёт id заданий
с `N·1000`, рубрик и критериев — с `N·100`. Диапазоны — договорённость
авторов seed, а уникальность гарантирует валидатор (§3.4).

### 3.2 Схема БД, миграция `004`

- Новая таблица `topics`: `id INTEGER PRIMARY KEY` (номер модуля), `title`,
  `intro`, `survey TEXT` (JSON конфига анкеты), `active`.
- `concepts.topic_id INTEGER REFERENCES topics(id)`.
- `chunks.topic_id INTEGER`. Все существующие чанки получают `topic_id = 1`:
  сейчас в RAG только материалы topic01.

### 3.3 Загрузка курса

`course/seed.load_course(conn, paths=None)` читает все `data/seed_topic*.json`,
склеивает их в один `Seed`, валидирует весь курс и применяет **одним**
`replace_seed`, который заодно пишет `topics`. Бот на старте и CLI
`python -m llm_tutor.course.seed` вызывают `load_course`. Флаг `--seed PATH`
остаётся для тестов и отладки одного файла.

### 3.4 Валидатор курса

К нынешним проверкам (цикл, битые ссылки, дубли внутри файла) добавляются:

- номера модулей уникальны, и номер в `topic.number` совпадает с NN в имени
  файла;
- id узлов, заданий, рубрик, критериев и ключи фактов анкеты уникальны
  **по всему курсу**;
- ребро `from → to` разрешено, только если `topic(from) ≤ topic(to)`. Ребро
  вперёд — ошибка;
- узлы блоков анкеты принадлежат модулю этого файла, и блоки покрывают
  каждый узел модуля ровно один раз;
- `assumed_by_confident` и `foundation` ссылаются на существующие блоки;
- **предупреждение** (не ошибка): жёсткое межмодульное ребро. CLI печатает
  такие рёбра списком.

### 3.5 `CourseGraph`

Граф один на весь курс. `concept.topic_id` известен, `graph.topic_of(node_id)`
отдаёт модуль узла, `graph.topic_nodes(n)` — узлы модуля в топопорядке.

`topo_order` становится лексикографическим
(`nx.lexicographical_topological_sort`) по ключу «модуль, порядок узла в
seed». Узлы модулей не перемешиваются, а внутри модуля сохраняется
авторский порядок. Порядок узлов topic01 после перехода закрепляется тестом.

## 4. Маршрут по модулям

### 4.1 Снимок и рабочий участок

**Снимок маршрута** (`SessionState.route`) покрывает **весь курс**: каждый узел
со своим статусом (`closed` / `current` / `claimed` / `ahead`). Так статус
«закрыт» переживает переход между модулями, а `diff_routes` не видит при смене
модуля сотни «добавленных» и «ушедших» узлов.

**Рабочий участок** — то, с чем ученик работает сейчас:

> узлы текущего модуля + их **незакрытые** транзитивные предки из прошлых
> модулей, в топопорядке.

Рабочий участок используют:
- `next_node_id`: планировщик выбирает следующий узел **только внутри
  участка**, и порядок 1 → 10 держится;
- `upcoming` и экран маршрута показывают только участок;
- проверка заявленного (🔍) в конце модуля берёт заявленные узлы участка.

**Текущий модуль** не хранится. Это модуль текущего узла, а если текущего узла
нет — первый по номеру модуль, где есть незакрытые узлы.

**Сообщение о пересмотре** (`diff_routes` → `is_significant`) учитывает только
узлы рабочего участка. Иначе первое расширение снимка (topic01 → весь курс)
или смена модуля выдали бы ученику «добавилось …» на сотню узлов.

**Заявленное из анкеты модуля.** `build_route` при существующем снимке берёт
заявленные узлы из снимка, а не из фактов: так узел, проверку которого ученик
не прошёл, не становится заявленным снова. Поэтому анкета модуля, пройденная
при существующем снимке, сама помечает узлы своих блоков «Уверенно» как
`claimed` в снимке, но только узлы со статусом `ahead`. Закрытые и текущий
узел она не трогает.

### 4.2 «Доказал — перестроили»

- **Вперёд.** Анкета модуля помечает блоки «Уверенно» как заявленные (🔍).
  Эти узлы маршрут пропускает и проверяет в конце модуля; подтверждённое
  закрывается. Механизм среза 23 работает без изменений, только на каждый
  модуль отдельно.
- **Назад.** Узел прошлого модуля перестаёт быть закрытым, если владение
  просело: повторение просрочено (режим `review`, это уже работает) или
  провалены задания, у которых он есть в `concept_weights`. Такой узел сам
  становится незакрытым предком и входит в рабочий участок текущего модуля.
  Второй путь работает, только если в заданиях проставлены межмодульные веса:
  это правило написания контента (§6.2) и пункт его ревью (§6.3).

### 4.3 Переход между модулями

После закрытия узла:

1. Если в рабочем участке остались незакрытые узлы, следующий узел выбирается
   как сейчас.
2. Иначе модуль пройден. Если он стал пройденным **только что** (до хода в
   нём были незакрытые узлы), ученик получает «🎉 Модуль N «…» пройден!».
3. Следующий — первый по номеру модуль с незакрытыми узлами. Вход в него
   идёт по правилу §5.2.
4. Незакрытых узлов не осталось нигде — «🎓 Курс пройден», вместо нынешнего
   `ROUTE_DONE_REPLY`.

Возврат к узлу прошлого модуля (из меню или потому что владение просело)
не объявляет этот модуль пройденным повторно.

### 4.4 Рабочая БД ученика

Миграция `004` и `load_course` проставляют узлам topic01 `topic_id = 1`.
Анкета topic01 уже пройдена, снимок маршрута при следующем ходе достраивается
узлами модулей 2–10 со статусом `ahead`. Ученик продолжает с того же места.
Перед миграцией делается бэкап `data/llm_tutor.sqlite3`.

## 5. Анкета, меню, тексты, промпты

### 5.1 Анкета по модулю

`student/survey.py` перестаёт хранить константы и принимает `SurveyConfig`
модуля (pydantic, из `topics.survey`). `Progress` и логика ветвления не
меняются, они параметризуются конфигом. `SELF_LEVELS` и `PRIOR_LEVELS`
остаются общими: подпись «Уверенно» по-прежнему не меняется.

- `is_completed(conn, config)` — есть ответы на все блоки модуля;
- `self_assessment(conn, config)` — профиль только текущего модуля;
- `claimed_concepts(conn)` — заявленное по всем модулям;
- `block_level(conn, concept_id)` — ищет блок в модуле узла.

### 5.2 Правило входа в модуль

> Если анкета модуля не пройдена, сначала анкета, потом урок.

Правило одно на все случаи:
- новый ученик → модуль 1 через «▶️ Поехали» (как сейчас);
- модуль пройден → «🎉 …» → анкета следующего модуля;
- прыжок из меню в будущий модуль → предупреждение (как сейчас для узлов
  «вперёд») → анкета этого модуля → выбранный узел.

Анкета работает так же, как сейчас: одно сообщение, `edit_text`, «‹ Назад».
В данных FSM дополнительно хранится номер модуля. Синхронный участок
хендлера `survey:*` до первого `await` сохраняется: атомарность держится на
`MemoryStorage`.

### 5.3 Меню «🎚 Темы»

Меню становится двухуровневым:
1. Список модулей со статусами ✅ пройден / ▶️ текущий / 🔜 впереди.
2. Тап по модулю показывает его темы с нынешними статусами (✅ ▶️ 🔍 🟢 🔜)
   и кнопку «← Модули».

Переход к теме работает как сейчас, плюс правило §5.2 для модуля, анкета
которого не пройдена.

### 5.4 Тексты и промпты

- Экран маршрута (`/plan`) получает заголовок «Модуль N/10 · название».
- Приветствие: «👋 Привет! Я тьютор по курсу mlcourse.ai: 10 модулей, от pandas
  до градиентного бустинга. Пара коротких вопросов — и подберу, с чего
  начать.»
- «С возвращением» называет модуль и тему.
- В трёх системных промптах (`llm/prompts.py`) зашитая «тема 1 «Pandas /
  EDA»» заменяется на «модуль N «название»» из пакета контекста
  (`core/context.py`).

### 5.5 RAG

`retrieve` фильтрует чанки по `topic_id ≤ текущий модуль`: в поиск попадают
материалы текущего и прошлых модулей, будущих — нет. CLI `ingest` получает
обязательный для новых загрузок флаг `--topic N`.

## 6. Контент модулей 2–10

Seed-файлы модулей 2–10 пишет Claude вручную, по образцу
`seed_topic01.json`.

### 6.1 Материалы

Для каждого модуля страницы mlcourse.ai (вводная и статья модуля)
сохраняются в markdown как `data/raw/topicNN_*.md`, так же как сейчас лежит
topic01. Точные URL сверяются с оглавлением книги в срезе модуля. Эти файлы —
опора для узлов и заданий, и они же загружаются в RAG через
`ingest --topic N`.

### 6.2 Правила написания

- Модули пишутся строго по порядку 2 → 10: межмодульные рёбра и веса
  ссылаются только на уже написанные модули.
- 15–25 узлов на модуль (у topic01 их 21). Узел — одна проверяемая идея, а не
  глава статьи. Узел без опоры в материалах допустим только как
  пререквизит-основа (как `python_basics` в topic01), с `source_url: null`.
- Рёбра внутри модуля и межмодульные рёбра назад. Межмодульные мягкие;
  жёсткие — только там, где без пререквизита модуль не понять (деревья →
  случайный лес). Каждое жёсткое межмодульное ребро обосновывается в
  сообщении коммита модуля.
- ≥ 2 заданий на узел. Типы как в topic01: в основном `choice` и `short`,
  их проверяет код, и 1–2 `open` с рубрикой на модуль.
- Задание, опирающееся на узел прошлого модуля, получает его в
  `concept_weights` со вторичным весом (0.3–0.5, как в topic01). Без этого
  не работает путь «назад» (§4.2).
- id заданий с `N·1000`, рубрик и критериев с `N·100`, ключи анкеты `tNN_…`.
- Анкета модуля: вопрос об уровне и 3–6 блоков, покрывающих все узлы.

### 6.3 Приёмка модуля

Claude — тоже LLM, поэтому написанный вручную контент проверяется так же
строго, как проверялся бы черновик генератора:

1. Валидатор курса и `uv run python -m llm_tutor.course.seed`: курс
   грузится, предупреждения разобраны. Тест на реальные файлы курса
   (появляется в срезе 24) проверяет все `data/seed_topic*.json`: курс
   валиден, у каждого узла ≥ 2 заданий, блоки анкеты покрывают модуль.
2. Адверсариальное ревью контента отдельным агентом:
   - эталонные ответы: верный вариант `choice` действительно верен,
     остальные неверны, `short`-эталон однозначен. Если ответ зависит от
     поведения кода (pandas, sklearn), он **проверяется запуском** во
     временном окружении uv (`uv run --with …`); в зависимости проекта эти
     пакеты не добавляются;
   - направление и жёсткость рёбер, межмодульных — особенно (§3
     архитектуры: здесь LLM ошибается чаще всего);
   - межмодульные `concept_weights` на месте;
   - узлы и задания опираются на материалы модуля;
   - анкета: вопросы понятны, блоки осмысленны.
3. Триаж и фиксы.
4. `ingest --topic N` материалов модуля.
5. `uv run pytest -q`.
6. Коммит `Модуль N: …`, фиксы ревью — `Аудит модуля N: …`.

Пользователь смотрит модули выборочно.

| 27 | Двухуровневое меню, `/plan`, тексты, промпты с модулем, фильтр RAG, `ingest --topic`; сквозной тест «модуль 1 → анкета модуля 2 → урок» на фейковом LLM | промпт содержит текущий модуль; RAG не отдаёт чанки будущего модуля |
| 28–36 | Модули 2–10, по одному на срез, строго по порядку | приёмка §6.3 |

## 8. Готовность

- `uv run pytest -q` зелёный.
- `python -m llm_tutor.course.seed` грузит десять модулей без ошибок, у
  каждого узла ≥ 2 заданий.
- Переход из модуля 1 в модуль 2 с анкетой проверен вручную в боте.
- `CLAUDE.md` описывает курс из десяти модулей.

## 9. Вне рамок

- **Генератор черновиков модулей.** Будет отдельной спекой и отдельным
  циклом позже; обкатывается на нейтральном материале, а не на модулях
  этого курса. Формат seed (§3.1) и валидатор курса (§3.4) для него уже
  будут готовы.
- Golden set грейдера для модулей 2–10 (остаётся только topic01).
- Межмодульная анкета «я знаю весь курс» и экзамен-пропуск модуля.
- Видео-лекции и домашние задания mlcourse.ai (в RAG идут только статьи).
- Ручной редактор графа.

## 10. Риски

| Риск | Что делаем |
|---|---|
| Ошибки в контенте: его пишет LLM | адверсариальное ревью каждого модуля; эталоны, зависящие от кода, проверяются запуском |
| Объём (~180 узлов, ~400 заданий): ревью «замыливается» | один модуль на срез и отдельное ревью на каждый |
| Лишнее жёсткое межмодульное ребро запирает модуль | по умолчанию мягкие; жёсткие видны в предупреждениях и обоснованы в коммите |
| Лексикографический топопорядок сдвинет порядок topic01 | тест на текущем seed в срезе 24 |
| Снимок маршрута на ~200 узлов замедлит ход (`mode_for_node` по каждому узлу) | замер в срезе 25; если медленно — пересчёт статусов только для участка и закрытых узлов |
| Межмодульные `concept_weights` не проставлены — «назад» работает только через повторение | правило §6.2 и пункт ревью §6.3 |
