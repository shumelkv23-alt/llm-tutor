# Дизайн: восстановление пароля по почте

> Дата: 2026-10-13. Добавляет в веб самостоятельный сброс пароля: ученик, забывший
> пароль, запрашивает письмо со ссылкой и задаёт новый пароль сам, без админа.
> Принципы проекта не меняются: состояния и вердикты считает код, секреты в БД не
> лежат в открытом виде, изменяющие запросы к `/api/*` идут через общий `api_guard`.

## 1. Зачем

Сейчас забывший пароль ученик — задача владельца: сброс есть только в админке
(`/api/admin/students/{id}/reset-password`), где админ вручную выдаёт временный
пароль и передаёт его ученику. При десятках учеников это ручная работа, а временный
пароль идёт по незащищённому каналу (переписка) и его знает админ. В спеке админки
(§2, п. 5) ссылка восстановления была помечена как следующая итерация — она и
делается.

## 2. Решения

1. **В письме — ссылка с одноразовым токеном**, а не временный пароль: пароль
   ученик придумывает сам, в почте и в журналах он не гуляет.
2. **Токен хранится хешем** (`sha256`), как токен веб-сессии: утечка файла БД не
   даёт сбросить чужой пароль. Сам токен — `secrets.token_urlsafe(32)`.
3. **Ссылка срабатывает один раз и живёт час** (срок настраивается). Одноразовость
   обеспечивает не проверка, а условный `UPDATE ... WHERE used_at IS NULL`
   (см. §5): победитель гонки получает `rowcount == 1`.
4. **Последняя заявка побеждает**: новый запрос гасит прежние токены ученика —
   ссылка из старого письма перестаёт работать.
5. **Ответ не зависит от того, есть ли такой email** (защита от перечисления
   адресов): один и тот же код и тело для существующего, несуществующего и
   некорректного адреса; счётчик лимитера растёт в любом случае; отправка письма
   уходит в фон после ответа.
6. **Отдельный лимитер** на запрос письма (`LoginLimiter`, 3 запроса / 15 мин):
   общий со входом смешал бы счётчики — неудачные входы блокировали бы запрос
   письма и наоборот. На сам сброс лимитера нет: токен — 32 случайных байта,
   перебор невозможен, а счётчик мешал бы честной опечатке.
7. **Сброс закрывает все сессии ученика**, включая ту, из которой его меняют:
   сброс пароля — реакция на «не помню/увели», чужие входы должны умереть.
8. **Почта — Gmail SMTP**, отправка через `smtplib` в потоке (`asyncio.to_thread`),
   без новых зависимостей. Пока нет «пароля приложения» Google — режим показа:
   письмо целиком пишется в журнал сервера, и сценарий проходится насквозь.
9. **Своих записей в `admin_log` нет.** Журнал — про действия админов, а карточка
   ученика рисует запись без автора как «аккаунт админа удалён»
   (`templates/admin_student.html`): самообслуживание выглядело бы там враньём.
   Пишется `logger.info` с одним id. След в админке — отдельная итерация (нужен
   nullable `admin_id` и правка карточки).
10. **Письма-уведомления «пароль изменён»** в этой итерации нет.

## 3. Сценарий

1. `/login` → «Забыли пароль?» → `/forgot-password`.
2. Email → `POST /api/auth/forgot-password` → на странице «проверьте почту».
3. Письмо: тема «Восстановление пароля в llm·tutor», ссылка
   `<PUBLIC_BASE_URL>/reset-password?token=…`.
4. `/reset-password?token=…` → форма нового пароля (от 8 символов, как везде).
5. `POST /api/auth/reset-password` → новый хеш, все сессии закрыты, блокировка
   входа снята → «пароль изменён» и ссылка на вход.
6. Вход новым паролем.

## 4. Данные

Миграция аккаунтов `004_password_reset.sql`, таблица `password_resets`:
`token_hash` (PK), `user_id` (FK на `users`, `ON DELETE CASCADE`), `created_at`,
`expires_at`, `used_at` (NULL — не использован). Индексы по `user_id` и
`expires_at`. Чистка — при каждой новой заявке (протухшие строки глобально и
прежние строки ученика), как чистка сессий в `create_session`; отдельного крона нет.

Функции в `web/accounts.py`:

- `create_reset_token(conn, user_id, *, now=None, ttl=RESET_TTL) -> str`;
- `reset_token_user(conn, token, *, now=None) -> User | None` — только чтение,
  для показа формы;
- `reset_password(conn, token, password_hash, *, now=None) -> int` — атомарное
  потребление токена, смена хеша и закрытие всех сессий одной транзакцией.

## 5. Атомарность: «ровно один сброс на токен»

`set_password` здесь не зовётся: он делает собственный `commit` и разорвал бы
связку «пометить токен → сменить хеш → закрыть сессии». Вместо этого один
синхронный блок без `await` внутри:

```sql
UPDATE password_resets SET used_at = ? WHERE token_hash = ? AND used_at IS NULL AND expires_at > ?
```

Условие `used_at IS NULL` — compare-and-swap на строке: `rowcount == 1` только у
победителя, проигравший получает «ссылка недействительна». Обращения к SQLite идут
из потока цикла событий (эндпоинты — `async def`), воркер uvicorn один
(CLAUDE.md), поэтому между `UPDATE` и `commit` никто не вклинится. Тяжёлый scrypt
считается до этого блока, в `asyncio.to_thread`.

## 6. Почта

`web/mailer.py`: протокол `Mailer` (`send`, `aclose`), две реализации.

- `SmtpMailer` — `ehlo → starttls → ehlo → login → send_message`, `EmailMessage` с
  UTF-8, соединение на письмо, таймаут из настроек. Ловит `smtplib.SMTPException`,
  `OSError`, `TimeoutError` и пишет в журнал **только класс исключения и SMTP-код**
  (у Gmail 535 — «не принят пароль») плюс подсказку про «пароль приложения»; ни
  пароля, ни токена, ни текста письма. Наружу не бросает никогда: письмо уходит
  фоном после ответа, и его сбой не должен ломать запрос.
- `LogMailer` — при ненастроенном SMTP письмо целиком уходит в журнал (WARNING).
  Это единственное место, где токен попадает в журнал; включается только когда
  почта не настроена, и на странице запроса об этом висит предупреждение.

Внедрение — как у `LLMClient`: `create_app(..., mailer=None)`, собственный мейлер
приложение закрывает в `lifespan`, внедрённый закрывает тот, кто создал.

Настройки (`config.py`, все с дефолтами — у существующих `.env` почтовых
переменных нет, а `extra="forbid"`): `SMTP_HOST`, `SMTP_PORT`, `SMTP_USER`,
`SMTP_PASSWORD` (`SecretStr`), `SMTP_STARTTLS`, `SMTP_TIMEOUT`, `MAIL_FROM`,
`MAIL_FROM_NAME`, `PUBLIC_BASE_URL`, `PASSWORD_RESET_TTL_MINUTES`,
`PASSWORD_RESET_LIMIT`. Признак готовности — `Settings.smtp_configured`: нужны и
адрес, и непустой пароль.

`PUBLIC_BASE_URL` берётся из настроек, а не из адреса запроса: за прокси заголовок
`Host` подконтролен клиенту, и в письмо ученику ушла бы ссылка на чужой сайт.

## 7. Эндпоинты и страницы

| | |
|---|---|
| `POST /api/auth/forgot-password` | `{email}` → всегда `200 {"ok": true}`; 429 при исчерпанном лимите |
| `POST /api/auth/reset-password` | `{token, password}` → 200; 422 с полем `password` (короткий пароль) или `token` (ссылка не годится) |
| `GET /forgot-password` | форма email; вошедшего — на `/profile`; баннер, если почта не настроена |
| `GET /reset-password?token=…` | годный токен — форма нового пароля, иначе сообщение и ссылка на запрос письма |

Обе страницы — `Cache-Control: no-store` (у второй секрет в адресе). Тексты
ошибок — в стиле проекта (`{"detail": {"field", "message"}}`), чтобы фронтенд
показал их рядом с полем. Формы наследуют `auth_base.html` и работают через общий
`auth.js`: у формы без `data-next` успех не уводит со страницы, а показывает
сообщение.

## 8. Что не делается

- Запись о самообслуживании в `admin_log` и показ её в админке.
- Письмо-уведомление о состоявшейся смене пароля.
- Проверка доступности SMTP на старте (как `check_llm_key`) — ошибка видна в
  журнале при первой неудачной отправке.
- Подтверждение email при регистрации.
