# Дизайн: админка (первая итерация)

> Дата: 2026-10-12. Добавляет в веб-приложение раздел `/admin` для владельца
> курса: кто учится и как, где ученики застревают, какие задания не работают, и
> минимум управления аккаунтами. Принцип проекта не меняется: админка только
> **читает** то, что посчитал код (журнал `events`, статусы тем), и не
> пересчитывает его по-своему; единственные записи — управление аккаунтами.

## 1. Зачем

Сейчас веб не даёт ответа на вопросы владельца:

- кто зарегистрирован, давно ли заходил, как далеко прошёл;
- на каких занятиях ученики бросают курс;
- какие задания почти никто не решает (сломанное задание или трудная тема);
- что делать, если ученик забыл пароль. Единственный админ-инструмент —
  CLI `import-legacy`; пароль сбросить нельзя вообще.

Контент (seed, конспекты) остаётся в git и правится руками — редактора курса в
админке не будет.

## 2. Решения

Приняты при проектировании, на согласование:

1. **Роль — флаг `users.is_admin`.** Первого админа назначает только CLI
   (`make-admin`), из веба роль не выдаётся и не снимается: захват аккаунта
   ученика не должен давать права админа.
2. **Не-админ видит 404, а не 403** на `/admin/*` и `/api/admin/*`: раздел не
   выдаёт своего существования. Гость на страницах — обычный редирект на вход.
3. **Роль читается из БД на каждый запрос** (вместе с сессией), поэтому снятие
   роли действует сразу, без выхода из сессии.
4. **Диалоги учеников в этой итерации не показываются.** Админ видит
   журнал `events` (что отвечал, с каким результатом) и статусы тем, но не
   `messages`. Переписка — личные данные; если понадобится, это отдельное
   решение с отдельной спекой.
5. **Сброс пароля — временный пароль, показанный один раз**, а не ссылка
   восстановления. Ссылка требует страницы приёма токена и канала доставки
   (почты нет). Минус: админ на мгновение знает пароль; ученик меняет его в
   профиле. Ссылка восстановления — следующая итерация.
6. **Сводная аналитика считается обходом БД учеников с кэшем на 60 с.** Данные
   учеников лежат в отдельных файлах (спека веба §2, п. 5), сводной таблицы нет.
   Для десятков учеников обход дёшев; для сотен потребуется сводная таблица в
   `accounts.sqlite3` (§9, «вне итерации»).
7. **Только чтение курса.** Публикацию модулей (`published`), перезаливку
   материалов и правку заданий админка не делает.
8. **Действия админа пишутся в журнал** `admin_log` (кто, что, над кем, когда).
   Пароль и токены в журнал не попадают.

## 3. Архитектура

Слои: `web → core/student/db`. Админка — часть `web/`; ядро не знает о ней.
Подсчёт по одной БД ученика берёт готовое из `core.overview`
(`topic_rows`, `module_rows`, `course_progress`) и `web.views.solved_items`:
своих формул статусов в админке нет.

```
src/llm_tutor/web/
  admin.py        данные: список учеников, карточка, воронка, трудные задания; кэш
  api_admin.py    /api/admin/*: сброс пароля, закрытие сессий
  pages_admin.py  HTML: /admin/students, /admin/students/{id}, /admin/course
  accounts.py     + is_admin, last_login_at, admin_log, список/поиск, роль
  security.py     + admin_user / admin_page_user (зависимости)
  cli.py          + make-admin, revoke-admin
  templates/      admin_students.html, admin_student.html, admin_course.html,
                  _admin_tabs.html
  static/css/admin.css, static/js/admin.js
migrations_accounts/
  003_admin.sql
```

CSP не меняется: JS и CSS в файлах, ширины столбцов (полосы прогресса) ставит
JS через CSSOM по `data-*`. Эндпоинты — `async def` (соединения SQLite живут в
потоке цикла событий).

### 3.1. Схема

`migrations_accounts/003_admin.sql` (`SCHEMA_VERSION` аккаунтов 2 → 3):

```sql
ALTER TABLE users ADD COLUMN is_admin INTEGER NOT NULL DEFAULT 0;
ALTER TABLE users ADD COLUMN last_login_at REAL;      -- NULL: ещё не входил

CREATE TABLE IF NOT EXISTS admin_log (
  id        INTEGER PRIMARY KEY,
  ts        REAL NOT NULL,
  admin_id  INTEGER NOT NULL,       -- без FK: журнал переживает аккаунт
  action    TEXT NOT NULL,          -- reset_password | close_sessions
  target_id INTEGER NOT NULL,
  details   TEXT                    -- JSON без секретов
);
CREATE INDEX IF NOT EXISTS idx_admin_log_target ON admin_log(target_id, ts);
```

`last_login_at` пишет `accounts.create_session` (его зовут и вход, и
регистрация); продление срока сессии входом не считается.

`User` получает поле `is_admin: bool = False`; **все** `SELECT` пользователя
(`resolve_session_info`, `get_user`, `credentials`, `find_user`) читают и его.
Тест сверяет, что нигде `is_admin` не остался дефолтным.

### 3.2. Доступ

- `security.admin_user` (API) и `admin_page_user` (страницы) строятся поверх
  `require_user`/`page_user`: вошедший не-админ → `HTTPException(404)`.
- Запросы на изменение идут через существующий `api_guard` (только JSON и свой
  `Origin`): CSRF закрыт тем же механизмом, что у остального API.
- Навигация: в `pages.render` пункт «Админка» добавляется в `nav` только если
  `user.is_admin`; ключ `admin` добавляется в `_TITLES`. Шаблон `base.html`
  не меняется.
- CLI: `python -m llm_tutor.web.cli make-admin --email …` и `revoke-admin
  --email …`. Нет аккаунта — ошибка с подсказкой зарегистрироваться в браузере
  (как у `import-legacy`). Команды идемпотентны.

## 4. Список учеников — `/admin/students`

Серверный рендер, `?q=` (подстрока имени или email, регистронезависимо),
`?page=` (по 50), сортировка по последней активности (новые первыми).

Столбцы:

| Столбец | Источник |
|---|---|
| Имя, email | `users` |
| Регистрация, последний вход | `users.created_at`, `last_login_at` |
| Последняя активность | максимум `messages.ts` и `events.ts` по БД ученика |
| Прогресс | `course_progress`: закрыто k из m занятий, процент |
| Состояние | `survey` / `in_progress` / `done` / `error` (как `views.course_card`) |
| Слабых тем | `topic_rows(...).weak` |

Ученик, записанный на курс, у которого файла БД нет, показывается с прочерками.
БД, которая не открывается (`sqlite3.DatabaseError`, `RuntimeError`), даёт
строку «Недоступен» и запись в лог — одна битая БД не роняет список (как в
`course_card`).

Сводка над таблицей: всего учеников, активных за 7 дней (по последней
активности), закончивших курс.

## 5. Карточка ученика — `/admin/students/{id}`

Только чтение, кроме двух действий (§6). Несуществующий id — 404.

- **Шапка:** имя, email, дата регистрации, последний вход, число активных
  сессий, пометка «админ».
- **Курс** (на каждый курс записи): прогресс по модулям (`module_rows`),
  таблица тем (название, статус, оценка владения в процентах, «мало данных» /
  «уверенно», слабая ли), результаты анкет (`survey.self_assessment`), число
  решённых заданий (`solved_items`).
- **Последние ответы:** 50 последних событий `events` с `item_id`: время,
  занятие, задание (id и первые 80 символов условия), источник, результат
  (верно / неверно / доля). Один ответ — одна строка, даже если задание
  меряет несколько концептов (ядро пишет по событию на концепт). Диалоги —
  нет (§2, п. 4).
- **Журнал действий админов** над этим учеником (последние 20).

Имя и прочий пользовательский текст выводит Jinja2 с автоэкранированием;
`innerHTML` в админке не используется вовсе.

## 6. Действия над аккаунтом

Кнопки на карточке; запрос идёт в `/api/admin/*`, подтверждение — штатный
`confirm-dialog`. Нельзя применить действие к самому себе (400 с подсказкой
«для своего аккаунта используйте профиль»): иначе админ закроет собственную
сессию или сменит себе пароль в обход проверки текущего.

- `POST /api/admin/students/{id}/reset-password` — генерирует пароль
  `secrets.token_urlsafe(12)` (16 символов), хеширует `scrypt` в потоке
  (`asyncio.to_thread`, как при регистрации), вызывает
  `accounts.set_password(..., keep_token=None)` — **все** сессии ученика
  закрываются, сбрасывает его счётчик неудачных входов, пишет `admin_log`.
  Ответ `{"password": "…"}` с `Cache-Control: no-store`; JS показывает его
  в диалоге один раз, с кнопкой «Копировать», и не кладёт ни в
  `localStorage`, ни в DOM после закрытия диалога.
- `POST /api/admin/students/{id}/close-sessions` — удаляет все строки
  `web_sessions` ученика, пишет `admin_log`. Ответ `{"closed": N}`.

Неизвестный `id` — 404. Ошибки — в том же формате `{"detail": {"message": …}}`,
что у остального API.

## 7. Аналитика курса — `/admin/course`

Данные — обход БД всех записанных учеников, результат кэшируется на 60 с
(`app.state`, ключ — курс); кнопка «Обновить» (`?refresh=1`) пересчитывает
сразу. Время расчёта показывается на странице («данные на 14:32»).

### 7.1. Воронка по занятиям

Строка на занятие в порядке курса, с заголовками модулей (модули
`published: false` не показываются). По `topic_rows` каждого ученика:

| Столбец | Определение |
|---|---|
| Дошли | статус `closed` или `current` у ученика, прошедшего анкету курса |
| Закрыли | статус `closed` |
| Слабо | закрыто и `weak` (⚠️: закрыто после двух ошибок) |
| Доля закрытия | закрыли / дошли |

Столбец «Дошли» — именно «дошли до занятия», а не «записаны»: знаменатель
должен показывать, где отваливаются те, кто начал. Занятия, до которых никто не
дошёл, показываются нулями, а не скрываются.

### 7.2. Трудные задания

Строка на задание банка. Источник — `events` с `item_id IS NOT NULL` и
`source IN ('autotest', 'checked', 'rubric')` (ответы на задания; события
`dialogue` и `self` — не ответы). Ядро пишет по событию на каждый концепт
задания с одним `ts` (`plan_evidence`), поэтому события одного ответа
сворачиваются по `(item_id, ts, source)`. Задания группируются по id из seed: он
стабилен (`seed` задаёт id явно), поэтому агрегат по разным БД корректен.
События по заданиям, которых нет в seed, пропускаются.

| Столбец | Определение |
|---|---|
| Задание | id, занятие, раздел, тип, первые 80 символов условия |
| Учеников | число разных учеников с ответом |
| Ответов | число событий |
| Верно | доля событий с `result >= 0.5` (как `solved_items`) |
| С первой попытки | доля учеников, чей первый ответ верный |
| Попыток на ученика | ответов / учеников |

Сортировка по умолчанию — доля верных по возрастанию; фильтр по модулю и по
типу. Строка с меньше чем 5 ответов или меньше чем 3 учениками выводится
приглушённой с пометкой «мало данных» и в сортировке по доле стоит в конце:
по двум ответам вывод о задании делать нельзя.

Это **подсказка, а не вердикт**: низкая доля верных значит «проверь задание»
(дистрактор, эталон, тесты), а не «задание плохое».

## 8. Тесты

Новый `tests/test_web_admin.py`, асинхронные, фикстуры `web`/`student`;
для курса — `use_lessons_course` и `tests/fixtures/lessons`.

- **Доступ:** гость на `/admin/*` → редирект на вход; не-админ → 404 на
  страницах и в API; админ → 200; снятие роли действует на следующем запросе
  без перелогина; изменяющий запрос с чужим `Origin` → 403.
- **Миграция:** аккаунты версии 2 с данными поднимаются до 3, пользователи и
  сессии целы, `is_admin = 0`; повторное открытие ничего не меняет.
- **CLI:** `make-admin` / `revoke-admin`, идемпотентность, неизвестный email.
- **`last_login_at`:** ставится входом и регистрацией, не меняется продлением.
- **Список:** поиск, страницы, сортировка, ученик без БД, битая БД не роняет
  страницу, XSS в имени экранируется.
- **Карточка:** ответы из `events`, заглушки без события, диалоги в страницу не
  попадают, 404 для чужого id.
- **Действия:** новый пароль входит, старый — нет; все сессии ученика закрыты;
  сессия админа цела; запись в `admin_log` без пароля; применение к себе → 400;
  ответ с `no-store`.
- **Аналитика:** воронка на подготовленных БД нескольких учеников (дошли /
  закрыли / слабо), доля верных и «с первой попытки» на известных событиях,
  порог «мало данных», события несуществующего задания пропущены, кэш (второй
  запрос не обходит БД) и `refresh`.
- **Утечки:** в HTML и JSON админки нет `password_hash` и подстроки `scrypt$`.

Браузерный тест (`e2e`) — один: админ сбрасывает пароль, видит диалог с
паролем, закрывает его; пароля после этого нет в DOM.

## 9. Вне итерации

- Просмотр диалогов учеников (приватность, §2 п. 4).
- Столбцы «Подсказок» и «Время решения»: `events.hints_used` и `time_spent`
  нигде в коде не заполняются (подсказки живут в `SessionState.hint_level`).
  Вернуть, когда появится источник данных.
- Расход на LLM: токены, стоимость, задержки, лимиты на ученика. Для этого
  нужна таблица вызовов и правки в `llm/`.
- Ссылка восстановления пароля вместо временного пароля.
- Сводная таблица активности в `accounts.sqlite3` (когда учеников станет
  сотни), частота выбора неверных вариантов у заданий `choice` (в `events`
  выбранный вариант не хранится).
- Удаление аккаунта, сброс прогресса по занятию, выдача и снятие роли из веба.
- Состояние сервиса (размер БД, пул, ошибки), журнал входов и неудачных
  попыток (лимитер живёт в памяти).
