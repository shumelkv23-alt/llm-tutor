# Ошибки и исключения

Программа падает — и это нормально: вопрос в том, что именно произошло и кто
об этом узнает. Занятие про две стороны одной темы: `assert` как договор о
поведении («так быть не должно, и если так — это баг») и исключения как способ
сказать «здесь всё пошло не так» и обработать это.

## Зачем

После занятия вы сможете:

- писать `assert` с сообщением и понимать, чем он отличается от `raise`;
- отличать предусловие от проверки данных пользователя;
- читать и писать `try / except / finally`, ловить конкретные исключения;
- понимать, что `finally` выполняется всегда — и при ошибке тоже;
- называть чужие ошибки по типу: `ValueError`, `ZeroDivisionError`,
  `KeyError`.

## Assert: договор о поведении

### Главное

`assert условие, "сообщение"` проверяет условие и поднимает
`AssertionError` с этим сообщением, если условие ложно. По сути это короткая
запись «если не выполнено — подними ошибку»:

```python
def check_positive(value: int) -> None:
    """Предусловие: значение должно быть положительным."""
    assert value > 0, "нужно положительное число"


try:
    check_positive(-1)
except AssertionError as exc:
    print("поймали:", exc)
```

Где `assert` уместен:

- **предусловие** — то, что вызывающий обязан обеспечить. «Кликов не может
  быть меньше нуля» — это утверждение о договоре, а не обработка ошибки;
- **микротест** — проверка чужой функции на известном случае. Так пишут тесты
  руками: вызвать функцию с эталонными аргументами и упасть с понятным
  текстом, если ответ не совпал.

Где `assert` не нужен: проверка данных, пришедших извне. Причина простая —
проверки `assert` **отключаются флагом `python -O`**, и код, который на них
полагался, молча продолжит работу с плохими данными. Для внешних данных —
`raise ValueError(...)`.

Разница между `assert` и `raise` — в адресате. `AssertionError` говорит
разработчику «здесь баг», `ValueError` — вызывающему «твои данные мне не
подходят». Ошибка без сообщения бесполезна: через день вы не вспомните, что
именно сломалось.

### Пример

```python
# Заведомо дефектная функция: делит нацело и молча врёт на дробях.
def ctr(clicks: int, shows: int) -> float:
    """CTR; содержит баг — возвращает int вместо float."""
    if shows < 0:
        raise ValueError("shows must be positive")
    return clicks // shows


def test_check_ctr(clicks: int, shows: int, expected_result: float) -> None:
    """Микротест: падает, если ctr посчитал неверно."""
    if ctr(clicks, shows) != expected_result:
        raise AssertionError("Wrong ctr calculation")


test_check_ctr(2, 2, 1.0)  # всё верно — функция молчит

try:
    test_check_ctr(1, 2, 0.5)  # баг: 0 вместо 0.5
except AssertionError as exc:
    print("поймали:", exc)

assert ctr(4, 2) == 2.0, "целые случаи считаются верно"
print("готово")
```

### Частые ошибки

- **`assert` для данных пользователя.** С `-O` проверка исчезнет вместе с
  защитой; для внешних данных — `raise ValueError`.
- **Ожидание, что `assert` «вернёт False».** Он не возвращает значение: он
  либо молчит, либо падает. `result = assert x > 0` — синтаксическая ошибка.
- **Ловить `AssertionError` там, где он должен проброситься.** Ошибка
  предусловия — сигнал вызывающему; перехватив её, вы спрячете баг.
- **Сравнение `float` через `!=`.** В тесте выше сравнивают именно так —
  потому что `ctr` обязан вернуть `float`, а `0 != 0.5` видно сразу; в
  настоящих проверках дробные числа сравнивают с допуском.

## Свои исключения и обработка

### Главное

Исключение — объект особого класса. Встроенные типы, которые встречаются
чаще всего:

- `ValueError` — значение не то (отрицательное число там, где нужно
  положительное);
- `ZeroDivisionError` — деление на ноль;
- `KeyError` / `IndexError` — нет такого ключа или позиции;
- `TypeError` — не тот тип («сложить число со строкой»).

Конструкция обработки:

```python
log: list[str] = []


def risky(shows: int) -> float:
    """Делит десять на показы; на нуле и на минусе ведёт себя по-разному."""
    if shows < 0:
        raise ValueError("shows must be positive")
    return 10 / shows


try:
    result = risky(0)
except ValueError:
    result = -1.0
except ZeroDivisionError:
    result = 0.0
finally:
    log.append("done")

print(result, log)
```

Правила, без которых обработка вредит:

- **Ловить конкретные типы.** Голый `except:` перехватит и опечатку в коде,
  и `KeyboardInterrupt` (Ctrl+C), и ошибку памяти — программа «не упадёт», а
  поведёт себя странно и молча.
- **`finally` выполняется всегда**: и когда всё прошло, и когда случилось
  исключение, и даже когда исключение пробрасывают дальше. Это место для
  очистки — закрыть файл, снять блокировку, записать в журнал.
- **`return` внутри `try` не отменяет `finally`.** Сначала выполняется
  `finally`, потом функция возвращает значение.
- **Необработанное исключение пробрасывают.** Если `AssertionError` из
  предусловия должен дойти до вызывающего — его не ловят, но `finally`
  всё равно отработает.

Своё исключение объявляют классом-наследником `Exception`:

```python
class WrongCtr(Exception):
    """CTR посчитан неверно."""
```

Такой класс полезен, когда ошибку нужно отличить от чужих: `except WrongCtr`
не поймает `ValueError` из глубины библиотеки.

### Пример

```python
def ctr(clicks: int, shows: int) -> float:
    """CTR; содержит баги: int вместо float, ValueError и деление на ноль."""
    if shows < 0:
        raise ValueError("shows must be positive")
    return clicks // shows


def safe_ctr(clicks: int, shows: int, log: list[str]) -> float:
    """Считает CTR безопасно: предусловие, два типа ошибок и журнал в finally."""
    try:
        assert clicks >= 0, "Clicks must be non-negative"
        return float(ctr(clicks, shows))
    except ValueError:
        return -1.0
    except ZeroDivisionError:
        return 0.0
    finally:
        log.append("done")


log: list[str] = []
print(safe_ctr(2, 2, log), log)     # 1.0 ['done']
print(safe_ctr(5, -1, log))         # -1.0: ctr поднял ValueError
print(safe_ctr(10, 0, log))         # 0.0: деление на ноль

try:
    safe_ctr(-1, 5, log)            # предусловие нарушено
except AssertionError as exc:
    print("AssertionError:", exc)

print(log)                          # finally отработал и здесь
assert log == ["done", "done", "done", "done"]
```

### Частые ошибки

- **Голый `except:`.** Ловит всё, включая опечатки в собственном коде:
  программа продолжает работать с мусором вместо того, чтобы упасть там, где
  ошибка.
- **Ловить `Exception` «на всякий случай».** То же самое, но вежливее:
  конкретный тип — часть документации о том, что вы умеете обрабатывать.
- **Забыть, что `finally` без `except` не спасает.** Если исключение не
  поймано, оно всё равно уйдёт наверх: `finally` — про очистку, а не про
  подавление.
- **Возврат из `except` без объяснения.** `return -1.0` прячет причину;
  либо пишите в журнал, либо выбирайте значение, которое нельзя спутать с
  настоящим ответом.
- **Своё исключение без наследования от `Exception`.** Наследник `BaseException`
  не поймается обычным `except Exception` и переживёт любую общую обработку.

## Итоги занятия

| Что | Что делает |
|---|---|
| `assert условие, "текст"` | предусловие или микротест; падает `AssertionError` |
| `raise ValueError("...")` | сообщить вызывающему, что данные не подходят |
| `try / except ValueError:` | обработать конкретный тип ошибки |
| `try / except ZeroDivisionError:` | деление на ноль — отдельная ветка |
| `finally:` | выполняется всегда: очистка, журнал |
| `class MyError(Exception)` | своё исключение, отличимое от чужих |

Правило занятия: `assert` — про договор с разработчиком, `raise` — про данные
снаружи; `finally` — про то, что должно случиться в любом случае.
